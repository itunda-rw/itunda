Quickstart

Create a payment, show the QR code and get a webhook when it is paid. Amounts are in RWF with no decimals.

1. Get a test key

Shared sample keys work for your first calls. Open the console for keys of your own, with test logs and webhooks. Test keys start with test_ and never move real money.

client key  test_ck_Dm8zN3pQe2vL4xKa
secret key  test_sk_Qe7vN2xDk4mZp9Lr
Keep the secret key private. Use the client key in the browser and the secret key only on your server.

2. Create a payment

curl "https://api.itunda.im/v1/payments" \
  -H "Authorization: Bearer test_sk_..." \
  -H "Idempotency-Key: order-1042" \
  -d amount=7500 \
  -d currency=RWF \
  -d method=qr
const res = await fetch("https://api.itunda.im/v1/payments", {
  method: "POST",
  headers: {
    "Authorization": "Bearer test_sk_...",
    "Idempotency-Key": "order-1042",
    "Content-Type": "application/json"
  },
  body: JSON.stringify({ amount: 7500, currency: "RWF", method: "qr" })
});
const pay = await res.json(); // show pay.qr_url
import requests

res = requests.post(
    "https://api.itunda.im/v1/payments",
    headers={"Authorization": "Bearer test_sk_...", "Idempotency-Key": "order-1042"},
    json={"amount": 7500, "currency": "RWF", "method": "qr"},
)
pay = res.json()  # show pay["qr_url"]

The response has status: "pending" and a qr_url. Show it as a QR code on your screen or receipt.

3. Simulate a payment

In the sandbox, open the qr_url and choose Paid, Failed or Refunded. Your webhook receives the matching event.

Authentication

Every request uses a secret key in the Authorization header. Keep keys on your server.

API keys

PrefixModeUse
test_sk_SandboxFake money. Safe for development.
live_sk_LiveReal payments. Issued after review.
Authorization: Bearer test_sk_...

Idempotency

Send an Idempotency-Key on every POST. If a request times out, retry with the same key and you will get the original result, not a second charge. Keys stay valid for 15 days.

Rate limits

Each key can make 100 requests per second. Over the limit you get 429 and a Retry-After header.

Refund a payment

POST/v1/payments/{id}/refunds

Send an optional amount for a partial refund. Leave it out to refund the full payment. Money returns to the customer’s Bank balance.

Webhooks

itunda sends a signed POST to your server when something changes, so you never need to poll.

Events

TypeWhen
payment.paidThe customer approved and money arrived.
payment.failedThe attempt was declined or cancelled.
payment.expiredThe QR code timed out.
refund.createdA refund was issued.

Verify the signature

Compute an HMAC-SHA256 of the raw request body with your webhook secret and compare it to the Itunda-Signature header.

Retries

Reply with any 2xx within 10 seconds. Otherwise we retry with growing gaps for 24 hours.

{
  "type": "payment.paid",
  "data": { "id": "pay_9f2c", "amount": 7500, "currency": "RWF" }
}
import crypto from "node:crypto";

function verify(raw, signature, secret) {
  const mac = crypto.createHmac("sha256", secret).update(raw).digest("hex");
  return crypto.timingSafeEqual(Buffer.from(mac), Buffer.from(signature));
}
import hmac, hashlib

def verify(raw, signature, secret):
    mac = hmac.new(secret.encode(), raw, hashlib.sha256).hexdigest()
    return hmac.compare_digest(mac, signature)

Errors

Errors use standard HTTP codes and a JSON body with a stable code you can match on.

{
  "error": {
    "code": "amount_invalid",
    "message": "amount must be a whole number of RWF."
  }
}
HTTPCodeWhat to do
400amount_invalidSend a positive whole number.
401key_invalidCheck the key and its mode.
409idempotency_conflictThe key was used with different parameters. Use a new key.
429rate_limitedWait for Retry-After seconds.
500server_errorRetry with the same idempotency key.

Payment window (SDK)

Open the itunda payment window from your page. The customer approves in the app, then you confirm the payment on your server.

Add the SDK

<script src="https://js.itunda.im/v1"></script>

Request a payment

FieldTypeDescription
methodstringQR, TILL, CARD or MOMO.
amountintegerAmount in RWF.
orderIdstringUnique per order, 6 to 64 characters.
orderNamestringShown to the customer in the window.
successUrl, failUrlstringMust include the origin, for example https://shop.example.rw/success.

Handle the redirect

After the customer approves, itunda sends them to successUrl with paymentKey, orderId and amount in the query string. The payment is not complete yet. Confirm it from your server.

Confirm on your server

POST/v1/payments/confirm
Check the amount. Compare the amount in the redirect with the price in your own database before you confirm. Never trust the browser.

Confirm within 10 minutes, or the payment is cancelled and the customer is not charged.

In the browser

const itunda = ItundaPay("test_ck_Dm8zN3pQe2vL4xKa");

  failUrl: "https://shop.example.rw/fail"

Build a mini app

Reach itunda users without an install. Your web app opens inside itunda, already signed in and ready to pay.

Configure

{
  "name": "Kigali Bakes",
  "permissions": ["profile", "pay"],
  "languages": ["en", "rw", "fr"],
  "entry": "https://bakes.example.rw"

Sign in and pay

import { itunda } from "@itunda/mini";

const user = await itunda.signIn({ scope: ["profile"] });
const pay = await itunda.pay({ amount: 4500, currency: "RWF" });

Business API

For POS vendors and shops with their own system. Push orders in, pull payments out and keep menus in sync.

Endpoints

EndpointDoes
GET /v1/paymentsList sales and ad-sourced payments.
PATCH /v1/menu/{id}Mark an item sold out.
POST /v1/eats/orders/{id}/acceptAccept an order and hand it to a Picker.
GET /v1/payoutsMonday payouts and cash-outs, to MTN MoMo or a bank account.

Business keys are issued from business.itunda.im. They start with biz_ and work like the keys in Authentication.

Accept an order

POST/v1/eats/orders/{id}/accept

Accept a new Eats order. Send prep_minutes so the customer sees a time. When the food is ready, itunda hands the order to a Picker.

curl -X POST "https://api.itunda.im/v1/eats/orders/ord_1042/accept" \\
  -H "Authorization: Bearer biz_sk_..." \\
  -d prep_minutes=12
{
  "id": "ord_1042",
  "status": "preparing",
  "prep_minutes": 12,
  "total": 7500,
  "currency": "RWF"
}

Mark an item sold out

PATCH/v1/menu/{id}

Set available to false and customers stop seeing the item right away. Set it back to true when you restock.

curl -X PATCH "https://api.itunda.im/v1/menu/itm_croissant" \\
  -H "Authorization: Bearer biz_sk_..." \\
  -d available=false
{
  "id": "itm_croissant",
  "name": "Croissant",
  "available": false
}

Common questions

Is there a sandbox?

Yes. Test keys never move real money, and you can simulate paid, failed and refunded payments.

Which currency?

Rwandan francs (RWF), whole numbers only.

Which languages do docs and apps support?

English, Kinyarwanda and Français, matching the itunda app.

Can I show ads in a mini app?

Ads on itunda are always labelled and never appear near balances, Send or Pay steps, or Messages. Mini apps follow the same rule.

When do I get live keys?

After a short review of your integration. Test everything in the sandbox first.
