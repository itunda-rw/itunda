### Added
- **`backend/`, `PAYMENTS.md`: itunda Payments — a real merchant payment gateway** mirroring Toss Payments' actual REST API contract, researched from `docs.tosspayments.com` per "toss have thing like passport, monitoring, internal tools, web tools like payments... search about toss online let's implement the same. do not imagine." Found a pre-existing `MERCHANT_SERVICES.md` in this repo that was exactly the failure mode being avoided here — an aspirational, never-implemented spec that invented an `Authorization: Bearer MERCHANT_API_KEY` scheme and webhook event names like `payment.received`, neither of which match how Toss (or any real gateway) actually works. Replaced that guesswork with the real thing:
  - Same endpoint paths, field names, and `status` enum as the real Toss Payments API (`READY → IN_PROGRESS → DONE`, `CANCELED`, `PARTIAL_CANCELED`, `ABORTED`, `EXPIRED`; `POST /v1/payments/confirm`, `POST /v1/payments/:paymentKey/cancel`, `GET /v1/payments/:paymentKey`), and the real auth scheme (`Authorization: Basic base64(secretKey + ':')`, a server-to-server merchant credential deliberately separate from the JWT bearer scheme used for end-user sessions — `backend/src/middleware/merchantAuth.middleware.ts`).
  - A confirmed payment is a **real, balanced ledger transaction** (`postLedgerTransaction`), not a status flag — debits the payer's actual itunda wallet, credits a new `merchant_payments_suspense` ledger account, and pushes a real `MerchantSettlement` record that shows up in the *existing* internal-tools System page's Merchant Settlement section (built earlier this session), rather than a parallel merchant-balance concept.
  - Real webhook delivery (`backend/src/services/webhooks.ts`) firing Toss's actual `PAYMENT_STATUS_CHANGED` event shape (`{ eventType, createdAt, data: Payment }`) to a merchant-registered URL.
  - Since itunda has no card networks or virtual accounts, the only real payment method is an itunda wallet balance — documented honestly in `PAYMENTS.md` rather than faking card support, and since itunda also has no separate payment-widget SDK, `checkout.url` points at a real page in this app (`src/pages/Checkout.tsx`, `/pay/checkout/:paymentKey`) where the payer logs into their actual itunda account and approves with their real wallet.
  - **Critical bug caught by actually retrying requests, not just writing the code**: the first version checked whether a payment was already `DONE` *before* checking for an `Idempotency-Key` replay, so a client legitimately retrying an already-succeeded `confirm` call (a dropped response, a timeout — the exact scenario idempotency keys exist for) got an `ALREADY_PROCESSED_PAYMENT` error instead of the original success replayed back. Caught by deliberately retrying a real confirm call against the running server and reading the *wallet balance*, not just the response — fixed by reordering the replay check before the status guards in both `confirmPayment` and `cancelPayment`, then re-verified the same way: confirming twice with the same key now returns an identical response both times and only ever moves money once.
  - Verified live end-to-end against the running backend: full create → payer-authorize → merchant-confirm → merchant-cancel lifecycle with real wallet balance deltas checked at each step (not just response bodies), idempotent replay confirmed to not double-charge, a real local HTTP receiver confirmed to actually receive the webhook payload, and the auth boundary confirmed to reject both an unknown secret key and a regular end-user JWT (wrong scheme entirely). Both backend and web frontend compile clean.
  - Full research citations, the real-vs-itunda deviation list, and an honest "not done" list (merchant self-signup, a merchant dashboard UI, Toss's real 7-attempt webhook retry policy, card/virtual-account support) are in `PAYMENTS.md`.

### Added
- **`backend/`, `src/pages/System.tsx`: real Gateway Passport + request monitoring**, researched from Toss's own engineering writeup (https://toss.tech/article/slash23-server) rather than guessed, per "toss have thing like passport, monitoring, internal tools... search about toss online let's implement the same." Found the real "System" internal-tools page already existed (12 sections: compliance, fraud, reconciliation, incidents, identity, ledger, rails, settlements, etc.) from earlier RBAC work, but had zero Passport/gateway concept and zero request-level monitoring — only business-domain stats. Built the two genuinely missing pieces and wired them into the existing page instead of standing up a redundant new app:
  - **Passport** (`backend/src/middleware/passport.middleware.ts`): a real per-request identity + device context, mirroring Toss's actual pattern — "유저 정보 호출 없이 Passport 정보를 통하여 유저에 대한 정보를 사용할 수 있습니다" (services use Passport instead of making their own redundant user lookup). Toss's version eliminates a real network hop per service; itunda is a single process, so there's no RPC to cut, but the pattern still paid for itself: `identity.controller.ts`'s `getMyIdentity`/`submitIdentity` each ran their own `users.find(...)` scan for the same caller — now both read `req.passport.user` instead, assembled once by `attachPassport` right after `requireAuth`, with a short-TTL (5s) in-memory cache so a burst of requests from one session doesn't rescan `users` every time (the same shape as Toss's Redis-backed cache, minus the pub/sub fan-out that only matters once there's more than one process). Deliberately scoped to the two routers that actually consume it (`identity.routes.ts`, `system.routes.ts`) rather than mechanically touched across all ~15 routers for its own sake — rolling out further is a 2-line change per router.
  - **Critical fix caught before shipping**: the first version of `getPassportPreview` (a new staff-only endpoint showing what a Passport looks like for the caller's own session) returned `req.passport.user` directly, which included the user's real bcrypt `passwordHash` — verified live via curl before catching it. Fixed by exporting `auth.controller.ts`'s existing `toPublicUser()` helper and using it as the *only* way `Passport.user` gets populated (both in the live request path and its cache), so no future consumer of `req.passport.user` can make the same mistake by construction, not just by convention.
  - **Monitoring** (`backend/src/services/metrics.ts` + `backend/src/middleware/metrics.middleware.ts`): real per-route request counts, status-code buckets, and latency (avg/p95), mirroring the shape of Toss's real Prometheus+Grafana stack (referenced in the same article) scaled down to what one Express process can honestly claim — no time-series DB, no cross-instance aggregation, no history past a restart, bounded to the last 500 samples/route so memory doesn't grow unbounded. Mounted globally (before the routers, so it also sees 404s and auth failures) and exposed via a new staff-gated `GET /system/metrics`.
  - Added both to the existing `System.tsx` internal-tools page as new "Monitoring" and "Gateway Passport" cards (auto-refreshing every 10s), consistent with the page's existing component style (`Metric`, `SectionTitle`, `SimpleRow`) rather than a new visual language.
  - Verified live via curl against the running backend: `/system/metrics` returns real, accumulating counts from actual requests (confirmed a `POST /api/v1/auth/login` call show up with real latency numbers); `/system/passport-preview` returns a real per-session Passport with the password-hash fix confirmed absent from the response; a regular `'user'`-role token correctly gets `403` on both new endpoints, matching the existing `/system/*` RBAC gate. Both backend (`tsc --noEmit`) and web frontend compile clean.

### Added
- **`android/`, Saronite mini-apps, critical integration**: wired React Native into itunda's actual Android app so the "All" tab's Mini Apps section (added in the previous pass) launches genuinely live mini-app screens, instead of standalone-only Saronite code with nothing reachable from the app. This was the deliberately deferred step from the last pass (see the `saronite/` entry below), done separately once the standalone module was already proven — and it surfaced six real, on-device problems in sequence, each found and fixed for real rather than glossed over:
  1. React Native 0.75.x's own Gradle plugin is built with Kotlin 1.9.24, which crashed configuring itunda's Kotlin 2.1.0 project outright. Fixed by upgrading to React Native 0.80.3 — found by `npm pack`-ing `@react-native-community/template` at several versions (0.75 through 0.86) and comparing which one's own template targets a Kotlin version compatible with itunda's, rather than guessing.
  2. itunda's `dependencyResolutionManagement { repositoriesMode = FAIL_ON_PROJECT_REPOS }` hard-rejected the React Native plugin's own repository registrations; relaxed to `PREFER_SETTINGS`, Gradle's documented mechanism for exactly this.
  3. The React Native CLI couldn't autolink because it expects an `android/` folder next to `package.json`, which the JS-only `saronite/host-app` deliberately doesn't have (the real Android project is the sibling `itunda/android`). Fixed with an explicit `react-native.config.js` pointing the CLI at the real app.
  4. **A real, reliable crash on every mini-app launch**: `SaroniteMiniAppActivity` read which mini-app to load from an Intent extra inside `getMainComponentName()`, but React Native's `ReactActivity` builds its delegate during `<init>` — before Android attaches the launch `Intent` — so `intent` was null and the Activity failed to instantiate every time (`Unable to instantiate activity ... NullPointerException`). Fixed by switching to one concrete Activity subclass per mini-app (`WalletBalanceMiniAppActivity`, `PayBillsMiniAppActivity`, `RewardTasksMiniAppActivity`), each hardcoding its own component name instead of depending on Intent timing.
  5. A second real crash immediately after: `IllegalStateException: You need to use a Theme.AppCompat theme (or descendant) with this activity` — itunda is a pure-Compose app with no AppCompat theme anywhere, but `ReactActivity` requires one. Added `androidx.appcompat` and a new `Theme.Itunda.MiniApp`, scoped to just the 3 mini-app Activities; `MainActivity`'s existing theme is untouched.
  6. A silent failure after that (no crash, just a black screen): logcat's `ReactNativeJS` tag showed `Incompatible React versions: react 19.2.7 vs react-native-renderer 19.1.0` — React Native 0.80.3 bundles its own renderer pinned to an exact React version, and a `^19.1.0` range in package.json let npm drift to a newer patch. Fixed by pinning `react` to the exact `19.1.0` across every package.json in the `saronite/` workspace.
  - Verified live end-to-end on the connected physical Android device (not an emulator, not just a clean build): installed the real app, navigated Home → All tab → Mini apps → Pay bills, and `PayBillsMiniAppActivity` genuinely booted Hermes, connected to the local Metro dev server over `adb reverse tcp:8081 tcp:8081`, executed the real JS bundle, and rendered real bill data live from itunda's backend (REG - Electricity, 35,000 RWF; WASAC - Water, 8,500 RWF) — a screenshot of the actual rendered screen confirmed this, not just a log line claiming success.
  - Full writeup of each bug and fix in `saronite/README.md`.

### Fixed
- **Critical, `backend/`, security**: started building real internal-tools access control and immediately found two live, exploitable gaps — closed both before building anything on top of them.
  1. **No role concept existed anywhere in this backend.** Every `/system/*` route (compliance queue, fraud cases, reconciliation batches, incident data, ledger view, merchant settlements) checked only `requireAuth` — meaning any authenticated **end-user** token, not just staff, could reach internal ops data. This was compounded by the web app's Profile page linking every logged-in user directly to a "System Control Plane" page backed by these same routes, with no role check in the UI either. Added a real `role` field to `User` ('user' | 'support' | 'compliance' | 'admin'), included it in the JWT claims at login/register, added a `requireRole(...)` middleware, and gated all of `/system/*` behind it. Added a real seeded staff account (`+250788000001`, role `admin`) to actually test this rather than assert it works. Hid the "System Control Plane" link in the web app's Profile page for non-staff roles, matching the backend gate.
  2. **`GET /system/identity` returned every user's identity/KYC credentials to whoever called it, with zero filtering** — and the web app's Profile page was calling this exact endpoint for *every regular user* just to check their own KYC status, meaning any logged-in user, before today, could already see everyone's NIDA submission records. Added a real self-service endpoint (`GET /identity/me`) that returns only the caller's own credentials (matched by the same holderName join key `submitIdentity` already uses — not redesigning that pre-existing data-model limitation here), and pointed the web app's Profile page at it instead. `GET /system/identity` remains as the legitimate ops-wide view, now correctly staff-gated.
  - Also fixed a migration hazard the role rollout would otherwise have hit silently: this backend persists its in-memory tables to `.data/store.json` and restores them on every restart (see `services/persistence.ts`), so the *old* snapshot — saved before `role` existed — would have silently overwritten the new seed data on the very next reload, restoring every user (including the new staff account, which wouldn't exist in the old snapshot at all) without a role. Added a migration-safe backfill in `hydrateMutableState` (defaults missing `role` to `'user'`) and an existence check that re-adds the staff seed account if a restored snapshot predates it — the same per-block "does this already exist" pattern used earlier this session for the Kotlin backend's `SeedDataRunner`.
  - Verified live end-to-end: a regular user token now correctly `403`s on `/system/compliance`; the seeded staff account correctly gets real compliance-queue data back; a regular user's own `/identity/me` call correctly returns only their own single credential, not the whole table; and after the migration fix, an existing (pre-role) snapshot correctly restores with every user backfilled to `role: 'user'` and the staff account present, instead of either silently missing or defaulting open.

Found and fixed two real bugs while wiring up idempotency: a bare `@Lob String` column defaulted to MySQL `TINYTEXT` (255 bytes) and silently truncated real request/response JSON until every write threw `DataIntegrityViolationException` (fixed with an explicit `TEXT` column); and `replayOrExecute` wasn't itself transactional, so a business write (e.g. a wallet debit) could commit while its idempotency record failed to save — a client retry with the same key would then find nothing cached and could double-charge (fixed by wrapping the whole replay-or-execute flow in one `@Transactional` boundary). Also fixed `SeedDataRunner` gating all seeding behind a single "does the demo user already exist" check, which meant every seed added after a local database already had that user (loans, contacts, holdings, savings goals seeded in this same change) would silently never run — each block now checks its own existence independently. Verified live end-to-end against real MySQL: bill pay/airtime, loan apply/repay, stock buy/sell, savings deposit/interest-claim, idempotency replay (same key+body → identical cached result, wallet debited exactly once; same key + different body → 409), and ownership checks with a real second registered account (403/404 on someone else's wallet/loan, empty contacts/loans instead of the demo user's, 404 on an interest jar that isn't theirs).
- Researched Toss Payments' own public idempotency-key spec (docs.tosspayments.com) against the `IdempotencyService` built in the previous change and found it diverged in two real ways, both now fixed: (1) keys were global rather than scoped per API route — reusing the same `Idempotency-Key` value on two different endpoints could have collided; `IdempotencyRecordEntity`'s primary key is now `"$method $path::$key"`, verified live that the same key value used on `bills/pay` then `loans/apply` runs as two independent requests instead of colliding. (2) There was no handling at all for two concurrent requests sharing the same key before the first finishes — both would find no completed record and both would run the business action; Toss Payments returns `409 IDEMPOTENT_REQUEST_PROCESSING` for exactly this case, which itunda now also does via an atomic claim step (`IdempotencyRecordRepository.insertIfAbsent`, `INSERT IGNORE` on a dedicated `record_key` primary key) before running the action. Building the claim step surfaced a second, subtler bug: the first attempt (catching `DataIntegrityViolationException` from a plain `saveAndFlush`) let a losing request's failed flush mark its own `REQUIRES_NEW` transaction rollback-only, so Spring's commit of that transaction threw an uncaught `UnexpectedRollbackException` — which, since nothing handled it, triggered an internal forward to `/error`, which isn't on the security allowlist, producing a bare `401` instead of the intended `409` (the same failure shape as the earlier Jackson-deserialization bug: uncaught exception → `/error` forward → blocked by security). Fixed by replacing the catch-based claim with `INSERT IGNORE`, which reports a lost race as a `0`-row return value instead of a thrown exception. Verified live: two truly concurrent identical requests now return exactly one `200` and one `409`, never two `200`s and never a `401`.
- Added the first real test coverage anywhere in `spring-backend` (previously zero): `LedgerServiceTest` using Kotest + MockK, matching Toss's own documented Kotlin testing convention (toss.tech/article/test-strategy-server) rather than defaulting to JUnit+Mockito. Covers balanced-leg posting, `LedgerImbalanceException` on unbalanced legs, and `InsufficientFundsException` on overdraft — each verified not to mutate any balance when rejected. Written Given/When/Then; required `IsolationMode.InstancePerLeaf` after the first version's sibling tests leaked mutated fixture state into each other (Kotest's default shared-instance behavior), which is itself a useful thing to have learned about this test framework this early.
- Checked every controller's error response shape against Toss Payments' real public API contract (docs.tosspayments.com/reference/error-codes: `{"code": "SCREAMING_SNAKE_CASE", "message": "..."}`) and found every error response across all 7 Kotlin controllers was an unstructured `{"error": "..."}` — each controller had its own redundant local `data class ApiError(val error: String)`. Replaced with a single shared `rw.itunda.core.web.ApiError(code, message)` used everywhere, with codes matching Toss's own naming exactly where there's a direct parity feature (`IDEMPOTENT_REQUEST_PROCESSING`, `INVALID_REQUEST`) and the same SCREAMING_SNAKE_CASE convention for this backend's own domain errors (`WALLET_NOT_FOUND`, `WALLET_NOT_OWNED`, `LOAN_NOT_OWNED`, `INSUFFICIENT_FUNDS`, etc. — 20+ codes total across wallet/bills/loans/stocks/savings/contacts/auth). Verified live: a 404 now returns `{"code":"WALLET_NOT_FOUND","message":"Wallet not found"}` and a 403 returns `{"code":"WALLET_NOT_OWNED","message":"That wallet does not belong to you"}`, with the normal success flow (login, wallet listing) unaffected.
- Added real JWT revocation (`:auth`'s new `TokenBlocklistService`) backed by **Redis** — the first genuine use of Redis anywhere in this repo, added for an actual reason rather than "Toss has one so we should too": a stateless JWT has no server-side record to delete on logout, so revoking a still-unexpired token requires a denylist every request checks, and that denylist has to self-expire (Redis TTL) or it leaks memory as a pure function of login volume. This closes `SECURITY.md`'s "Token revocation... not yet built" remediation item — there was previously no logout endpoint at all. Every issued JWT now carries a `jti` (unique id); `JwtAuthenticationFilter` rejects a token whose `jti` is revoked, in addition to its existing checks. Added `POST /api/v1/auth/logout` (revokes the presented access token, and the refresh token too if supplied) and `POST /api/v1/auth/refresh` (issues a new access+refresh pair and immediately revokes the old refresh token — rotation, so a stolen-but-already-rotated refresh token is a detectable blocked replay instead of a silently reusable long-lived credential, matching the standard JWT+Redis rotation pattern this was researched against). Verified live against a real Redis container: logged in, used the access token successfully, called logout, confirmed the *same* access token now 401s; separately, refreshed with the original refresh token (got a new working access token), then tried to refresh again with that same original refresh token and confirmed it's rejected as already used.
- Added Redis-backed rate limiting (`:auth`'s new `RateLimiter`) on `POST /auth/login` (5/minute) and `POST /auth/register` (3/10 minutes), keyed by phone number rather than IP — the actual asset being brute-forced is one account's password, and a real attacker rotates source IPs long before they rotate target phone numbers. This closes `SECURITY.md` gap #4, "No rate limiting... no brute-force protection on login," found actionable by checking Toss's own real public Gateway architecture write-up (toss.tech/article/22910), which explicitly lists rate limiting as one of the Gateway's core responsibilities alongside auth and circuit breaking. itunda doesn't have a separate gateway service (standing one up purely to rate-limit two endpoints would be solving a problem this app doesn't have yet at its current single-service scale), so the same concern is handled directly in `AuthService` via a fixed-window counter: a single atomic Redis Lua script (`INCR` + conditional `EXPIRE`) per `checkLimit` call, so two concurrent requests can't both observe count==1 and both skip setting the TTL. Verified live: 5 wrong-password login attempts for one phone number all correctly 401, a 6th correctly 429s with `RATE_LIMITED`, and a different, never-attempted phone number is unaffected (401 for unknown number, not 429) — confirming per-key isolation.
