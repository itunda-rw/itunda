# Self-Check: Am I Vibe Coding?

**Run this checklist on your own work before considering it done.** "Vibe coding" (a term
coined by Andrej Karpathy, 2025) describes accepting AI-generated code because it *looks*
right without verifying it *is* right. This doc names the real, measured failure modes
that produces, points to real instances itunda has already hit, and gives a direct
self-check checklist. Companion to
[`docs/UI_UX_GUIDELINES.md`](UI_UX_GUIDELINES.md)/[`docs/ARCHITECTURE_GUIDELINES.md`](ARCHITECTURE_GUIDELINES.md)
(what good code/UX looks like) — this doc is about catching yourself *not* meeting them.

## The real, measured failure modes

Sourced from Veracode's LLM code-security analysis, the Cloud Security Alliance's 2026
research notes on AI-generated-code vulnerability surges, and Snyk/Trend Micro's package-
hallucination research:

1. **Security flaws in ~45% of AI-generated code samples** (OWASP Top 10 class — injection,
   broken access control, etc.) — because the model optimizes for code that *looks*
   correct, not code that's been checked against a real threat model.
2. **Hallucinated package names in ~20% of code samples** across major models (some
   measured as high as 64%) — a model invents a plausible-sounding dependency that doesn't
   exist. Attackers register those exact names ("slopsquatting") and ship malware under
   them; ~43% of hallucinated names recur across prompts, making them predictable targets.
3. **Secrets exposed in AI-assisted commits at ~2x the rate** of human-only commits, most
   often API keys/DB credentials placed in client-side code where browser DevTools can
   read them directly.
4. **Test coverage collapse** (industry data: from a ~68% norm down to ~12% on heavily
   AI-assisted codebases) from accepting generated snippets without writing or checking
   the tests that would catch a regression.
5. **"Looks correct" code that concentrates real problems in error handling, edge cases,
   and security boundaries** — passes a shallow review/build, then breaks under real
   production load, because the shallow review never exercised those paths.
6. **API/interface contracts silently violated** — generated code that doesn't match an
   existing type signature, swallows an error it should propagate, or duplicates logic an
   existing shared function already covers, because the model didn't actually check.

## Real instances itunda has already hit — this is not hypothetical

- **A "looks correct" fake-success bug, the worst version of #5**: `services/backend`'s
  original `TransferController`/`TransferService` called a mocked `LedgerService` whose
  `.save()` calls were commented out — it returned HTTP 200 `"SUCCESS"` for a money
  transfer while persisting nothing at all. It passed a shallow check (endpoint responds,
  returns success) while doing the exact opposite of its job. Found and fixed; see
  `docs/ARCHITECTURE.md` §1.
- **A hallucinated stack, the same failure mode as #2 but for documentation, not
  packages**: `CONTRIBUTING.md` described NestJS/TypeORM/npm/Jest-style e2e tests — none
  of which this repo uses — almost certainly because it was generated by pattern-matching
  "what a typical Node.js project's CONTRIBUTING.md looks like" rather than checking this
  repo's real stack. Fixed 2026-08-19 (see `docs/UI_UX_GUIDELINES.md`'s own git history).
- **Duplicated logic instead of the real shared component, #6**: 415+ raw
  `<button className="itunda-btn ...">` in `BankDashboard.tsx` instead of the real shared
  `IdsButton` — accumulated because each new screen's author (human or agent) didn't check
  whether a shared component already existed first. See
  `ARCHITECTURE_GUIDELINES.md` §3.
- **A repeated structural gap, same root cause every time**: adding a new
  `LedgerAccountType` without a matching `SEED_IDS` row real-500s live — hit as a *class*
  of bug multiple times before a guard script was wired into CI (see
  [[feedback_ledger_account_seed_bug_class]] session memory) — the pattern of "add the
  obvious new case, miss the less-obvious matching one" is exactly what happens when a
  change is accepted because it looks complete, not verified against every real call site.
- **"Build succeeded" that wasn't**: a local Docker build printed `BUILD SUCCESSFUL` and
  exited 0 while silently never producing the image (a disk-space `input/output error`
  swallowed inside the layer-export step) — see [[feedback_docker_build_killed_disk_pressure]]
  session memory. A green build/exit-code is necessary, never sufficient, evidence that
  something actually happened.
- **"Everything in one file," the most-repeated real mistake in this codebase**:
  `BankDashboard.tsx` grew to 23,000+ lines holding every product, one reasonable-looking
  addition at a time — never one bad decision, always "it's easier to add it here than set
  up a new file/module." A 2026-08-19 sweep found this is not one file's problem: 87 more
  files across web/Android/iOS are already over 500 lines the same way. Real, automated
  guardrail now exists: `scripts/file-size-lint.py` (see `ARCHITECTURE_GUIDELINES.md` §2)
  — run it before finishing any change that touches an already-large file.
- **itunda's own JWT secret handling is the CORRECT counter-example, worth copying**:
  `application.yml`'s `secret: ${JWT_SECRET:itunda-dev-secret-do-not-use-in-production}` —
  externalized via env var, with a fallback that's both obviously fake AND says so in its
  own name. This is the pattern any new secret/credential should follow, not a hardcoded
  literal.

## The self-check checklist

Before saying a task is done, answer each of these about your OWN just-written change —
not in the abstract, against the actual diff:

1. **Did I add a new dependency?** → Have I confirmed it's a real package (not a plausible-
   sounding invented name) by actually checking it resolves — `yarn info <pkg>` or the
   registry — not just because it "sounds like something that should exist"?
2. **Did I add or touch anything handling a secret, token, or credential?** → Is it read
   from an env var / secret store, never a literal in source, and does any fallback value
   make it impossible to mistake for a real production secret (see the JWT example above)?
3. **Did I add input handling (a form, an API endpoint, a query param)?** → Have I checked
   it against real injection/access-control risks, not just the happy path? Does it
   actually enforce ownership checks (a user can't act on someone else's resource) the way
   every existing money-moving endpoint in this repo already does? If it takes a resource
   id, check one level deeper than the HTTP status: does the "doesn't exist" case and the
   "exists but isn't yours" case return byte-identical response bodies (same `code`, same
   `message`), not just the same status code? A same-status-different-body pair is a real,
   twice-independently-found bug in this exact codebase (see `project_itunda_idor_audit`
   memory's pass 9 and its 2026-09-04 continuation) — always name-searchable via the
   pattern's SHAPE (two sibling exceptions for the same resource, one for missing/one for
   unauthorized), not any specific exception-naming convention, since the second instance
   was missed by a grep for the first instance's naming style alone.
4. **Would my change survive being read by someone who didn't write it?** → Re-read the
   diff as if reviewing a stranger's PR. Does every function do what its name says (no
   hidden side effect)? Is there a nested ternary, an unnamed magic number, a duplicated
   near-copy of an existing function?
5. **Did I actually run it, or does it just compile?** → A green build/typecheck/lint is
   necessary, never sufficient (see the Docker example above). Did you exercise the real
   path — a live click-through, a real API call, a real test — not just "no red text"?
6. **Did I add a new pattern, convention, or architectural decision?** → Have I checked
   whether an existing one already covers this (grep first), and if this one is genuinely
   new, did I write it down in `ARCHITECTURE_GUIDELINES.md`/`UI_UX_GUIDELINES.md` so the
   next agent doesn't have to rediscover it or invent a THIRD inconsistent version?
7. **Am I adding code to a file that's already huge, instead of extracting?** → Run
   `python3 scripts/file-size-lint.py` before you finish. This is the single most-repeated
   real mistake in this codebase's own history — `BankDashboard.tsx` reached 23,000+ lines
   this way, one reasonable-looking addition at a time, and a 2026-08-19 sweep found the
   identical pattern on 87 other files across every platform. "It's just one more function"
   is exactly how every one of those got that way. If the file you're editing is already in
   `scripts/file-size-baseline.json`, prefer a new file/module for what you're adding over
   extending it further.
8. **Am I claiming something is fixed/verified that I only assumed?** → Every "fixed"/
   "verified" claim in a commit message or summary should trace to something you actually
   observed (a test result, a live response, a rendered screenshot) — not "it should work
   now." If you didn't verify it, say so honestly instead of implying you did.
9. **Does this documentation/comment describe what's REALLY here?** → Before writing a
   doc, comment, or commit message describing the stack/behavior, check the actual code —
   don't pattern-match to what a typical project "usually" looks like (the CONTRIBUTING.md
   failure above).

If any answer is "no" or "I'm not sure," that's the actual work remaining — not a detail
to skip because the code already looks done.
