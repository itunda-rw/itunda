# Engineering status contract

The current GitHub Actions run observed for commit bec311921fc2b1ddb18b2a740926b9ab379607c6 was pending, with its listed jobs queued. This is not a passing build. The combined commit-status endpoint returned no legacy status entries; that is not proof of success. Reading main branch protection was denied by the connector, so required checks remain unverified.

The existing Ops MFE is an operations dashboard, not yet a complete engineering status console. The first UI increment is a read-only view. Its endpoint is deliberately placed under `/api/v1/system/**`, which the current Spring Security configuration protects with `hasRole("ADMIN")`. A read-only Spring controller and GitHub check-runs adapter have now been added on the PR branch. They are not yet build-verified or deployed. The endpoint fails closed with HTTP 503 when configuration/provider access fails; never put GitHub credentials in the browser.

Each check must include its name, explicit result, immutable commit SHA, source, observation timestamp, environment, and details URL where available. Only explicit, fresh success for the same required commit may count as green. Pending, failed, stale, unknown, missing, mismatched-commit, provider-error, and empty results must never be rendered as success. A hidden UI tab is not authorization; enforce staff permissions server-side.

Configure server-side properties from deployment secrets/environment: `ITUNDA_ENGINEERING_REPOSITORY` (`owner/repo`), `ITUNDA_ENGINEERING_BRANCH` (defaults to `main`), `ITUNDA_ENGINEERING_REQUIRED_CHECK_IDS` (comma-separated exact check-run names, chosen only after the repository's required-check policy is verified), `ITUNDA_ENGINEERING_GITHUB_TOKEN` (recommended server-side token), and `ITUNDA_ENGINEERING_ENVIRONMENT` (`local`, `sandbox`, `staging`, or `production`). These map to `itunda.engineering.*` properties. Without a repository and a non-empty required-check list the endpoint returns 503, not success. The adapter currently reads GitHub check runs for the exact current branch SHA; classic commit statuses and paginated results are not yet included.

Acceptance tests should cover success, failure, pending, unknown, stale results, missing or mixed commit SHAs, provider timeout, empty results, unauthorized access, and secret leakage. A controller test now covers successful pass-through and fail-closed provider/configuration errors. Full module build/test and live authenticated endpoint verification remain required before deployment. The UI should reuse Itunda design tokens and clearly show source and freshness.


The response must include a non-empty `requiredCheckIds` array maintained by server-side configuration or repository policy. The UI may declare readiness only when every required ID has exactly one current check with explicit `success` for `headSha`; extra successful checks must not compensate for a missing required check. If the required list is absent or empty, readiness is unknown/false.
