01 · Principles

Quiet by default.
Precise when it matters.

The system is built around a small set of decisions that should survive every product surface: clear hierarchy, restrained decoration, tactile feedback, accessible defaults and predictable behavior.

Clarity

One dominant action, readable hierarchy and no decoration that competes with the task.

Consistency

Shared tokens and components prevent every product team from inventing its own version of the same interaction.

Care

Long text, larger text, dark mode, reduced motion and screen readers are component requirements, not cleanup work.

Product first

IDS provides the hard decisions so product teams can spend their time solving Rwanda's real customer problems.

06 · Foundations / Motion

Immediate, then settled.

Motion should communicate cause and effect. Fast feedback is immediate; larger surfaces settle with a softer easing curve. Reduced motion removes decorative animation.

140ms · Fast

Press, focus, color and micro-feedback.

220ms · Normal

Surface transitions and component state changes.

420ms · Slow

Large surface movement where spatial context matters.

Reduced motion

Transitions and loading animations are disabled when the OS asks for less motion.

15 · Quality gates

Ship the edge cases, not just the happy path.

A component is ready when its behavior remains coherent under real product conditions.

Long content

Wrap, truncate or scroll intentionally. Never let content silently collide.

Large text

Layouts must survive accessibility text scaling without losing hierarchy.

Keyboard & screen reader

Focus order, labels, roles and state announcements are part of the component.

Dark mode

Semantic tokens change surfaces and emphasis without changing meaning.

Reduced motion

Every non-essential transition has a reduced-motion behavior.

Touch targets

Interactive controls maintain a practical minimum target size across platforms.

16 · Quality / Accessibility

Accessibility is a component feature.

IDS requires keyboard focus, larger text, screen-reader semantics, sufficient touch targets, reduced motion and useful labels. The same contract should hold across VoiceOver and TalkBack.

Large text

Content reflows instead of clipping or hiding actions when text grows.

Screen readers

Interactive controls expose purpose, state and focus order instead of visual appearance alone.

Reduced motion

Decorative movement disappears while functional state changes remain understandable.

Contrast & targets

Text remains readable and interactive targets remain comfortable on small screens.

IDS 3.0 · Component API

One primitive, two consumption modes

Simple components stay simple. Complex components expose controlled composition instead of accumulating endless props.

Flat API

Preferred for stable, common cases: Button, Badge, Avatar, Switch and other low-variation primitives.

<Button variant="primary" size="large">Send</Button>

Compound API

Preferred where structure varies: Card, Sheet, Dialog, complex List and data-heavy surfaces.

<Card>
  <Card.Header>...</Card.Header>
  <Card.Body>...</Card.Body>
</Card>

API rules

  • Use semantic intent names, not raw colors or arbitrary visual props.
  • Do not expose props that duplicate a foundation token without a behavioral reason.
  • Prefer composition when new requirements would otherwise create a growing prop matrix.
  • Keep platform-native behavior behind the same semantic contract.

Build the system without breaking the product
